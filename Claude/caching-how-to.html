> Implementation Guide

How Prompt Caching Works

Caching relies on strict prefix matching, meaning the system checks your request from the very first byte. If any part of the beginning changes, the entire cache is broken.
Set your model and effort level before starting a task, as changing either one mid-conversation invalidates the prompt cache and increases costs.

/01 Core Mechanisms

> Strict Hierarchy

The API always arranges your data in a specific order: Tools, System Instructions, and then Messages. Changing a tool definition at the top will instantly ruin the cache for the entire request.

> 20-Block Lookback

During a chat, the system checks up to 20 previous text blocks to find a matching save point. If the chat grows beyond this limit, you must set new breakpoints to avoid losing the cache.

> Token Limits

Caching does not work on short prompts. You must meet a minimum token threshold, such as 1,024 tokens for Claude 3.5 Sonnet. If the prompt is too short, the API processes it normally.

(i) KNOW YOUR MODEL

The Claude model ecosystem is tiered by computational capability, latency, and cost to address different architectural workloads:

  • > Claude Haiku: The fastest and most cost-effective model in the lineup. It is engineered for near-instant latency, high-volume API requests, simple data classification, and lightweight agentic routing.
  • > Claude Sonnet: The optimized workhorse. It offers the best balance of speed and advanced intelligence, widely considered the default choice for software engineering, complex coding tasks, and multi-step autonomous workflows.
  • > Claude Opus: The heavyweight reasoning engine. It operates at a higher cost and lower speed but provides top-tier performance for highly complex logic, deep analytical tasks, and extended strategic planning.
  • > Claude Fable: A premium, highly specialized model tier designed for advanced narrative, nuanced behavioral emulation, and deeply complex contextual generation. Operating at the highest price point, it is reserved for extraordinary creative or specialized reasoning.

/04 Guidelines

1. Front-Load Your Heavy Context:

Place your largest, most permanent data at the absolute beginning of your interaction. Instead of trickling in rules over multiple turns, provide your extensive reference files, API documentation, and overarching project instructions in your very first prompt so the system locks them into a stable prefix.

2. Adopt an Append-Only Mentality:

Once your baseline context is established, treat it as entirely immutable. If a local file changes or you need to adjust a rule, do not edit your initial system setup. Simply send a new message (e.g., "Update: I changed the CSS file locally, use this new version"), which safely adds to the history without destroying the foundational cache.

3. Ban Volatile Core Instructions:

Never inject dynamic variables, such as the current timestamp or rotating request IDs, into your project's custom instructions or system prompts. Because the caching engine relies on strict prefix matching from the very first byte, a changing variable instantly invalidates the entire cache chain.

4. Summarize Long Threads In-Place:

As your chat history grows toward the context limit, do not start a brand-new session to clear the console. Instead, ask Claude to summarize the progress directly within the active thread. This allows the API to read the massive history at a 90% discount to generate the summary using cache-safe compaction.

5. Defer Heavy Tools and Optimize TTL:

If you are utilizing agentic workflows with dozens of tools, pass lightweight tool names (stubs) and let the model search for the details when needed to keep the prefix perfectly stable. Furthermore, if you frequently pause to read code or think between prompts, configure a 1-hour Time-To-Live (TTL) instead of the default 5-minute window to prevent your cache from expiring during your idle time.
