> Implementation Guide

How Prompt Caching Works

Caching relies on strict prefix matching, meaning the system checks your request from the very first byte. If any part of the beginning changes, the entire cache is broken.
Set your model and effort level before starting a task, as changing either one mid-conversation invalidates the prompt cache and increases costs.

/01 Core Mechanisms

> Strict Hierarchy

The API always arranges your data in a specific order: Tools, System Instructions, and then Messages. Changing a tool definition at the top will instantly ruin the cache for the entire request.

> 20-Block Lookback

During a chat, the system checks up to 20 previous text blocks to find a matching save point. If the chat grows beyond this limit, you must set new breakpoints to avoid losing the cache.

> Token Limits

Caching does not work on short prompts. You must meet a minimum token threshold, such as 1,024 tokens for Claude 3.5 Sonnet. If the prompt is too short, the API processes it normally.

/02 Optimized Developer Workflow

To maximize savings, separate your prompt content from the most permanent to the most changeable.

1
Top Layer (Highly Static)

Place all global tool definitions and core system personas here. This area almost never changes.

> cache_control: { type: "ephemeral", ttl: "1h" }
2
Middle Layer (Semi-Static)

Place project files or retrieved documents here. It stays the same during a single conversation session.

> cache_control: { type: "ephemeral" }
3
Bottom Layer (Dynamic)

The active turn-by-turn chat history. Changes on every single request.

> Append new messages here only

/04 Guidelines

> RULE 01

Static First, Dynamic Last

The cache checks from token zero. Place tool schemas and main instructions at the absolute top of the payload. Place volatile user messages at the very bottom. This ensures changes at the bottom do not invalidate the cached prefix at the top.

> RULE 02

Append Updates, Never Mutate

Never update a system prompt mid-session to inject timestamps or dynamic context. Changing a single byte in the system prompt breaks the entire cache chain. Always append new information as a distinct message at the end of the history array.

> RULE 03

Defer Heavy Tool Schemas

Sending full definitions for dozens of tools wastes prefix space and inflates the payload. Mark non-essential tools as lightweight stubs with defer_loading: true and rely on Tool Search to load them dynamically.

> RULE 04

Reuse State for Summaries

When generating session summaries, do not manually strip away the original system prompts to "save space." Send the summary request with the original history completely intact to secure the 90% read discount on the entire lookup.

> RULE 05

Economic TTL Routing

Default to a 5-minute TTL for automated agentic loops where API requests occur rapidly. Switch to a 1-hour extended TTL only for human-in-the-loop applications where users pause to read or think between queries.
